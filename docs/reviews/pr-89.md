## Findings

### P1-1: The promotion concurrency group can drop a pending push

Status: fixed in `cdc3ed77`.

Open at: `e8a8cd9f3407a5f4a345607d17d8780d83b82bb5`.

File: `.github/workflows/night-promote.yml:28-30`.

Trigger: one `night-promote` run is active, one run waits, and another push to `main` starts a run in the same concurrency group.

Expected: every push to `main` gets an ordered promotion check (D-1202, PR-108 exit test 5).

Actual: the workflow sets `cancel-in-progress: false` but leaves the default pending-run policy. GitHub keeps one pending run per group and cancels an existing pending run when a new run queues. The middle push can therefore lose its workflow run and promotion artifact. A later PR run only examines its own merged PR and cannot restore the dropped promotion.

Consequence: the promotion for a merged PR can go missing. The required night gate can stay red until another night succeeds, even when the dropped PR had a green night on the failed range. GitHub documents this pending-run replacement behavior in [Control the concurrency of workflows and actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), accessed 2026-09-27.

Correction: retain every push in an ordered queue, or make a later run reconcile promotions for each skipped push. Add a regression check for the queue policy and verify that several pushes queued behind one active run each produce a promotion result.

Regression check: a workflow test must prove the workflow retains multiple pending runs. A run with several rapid pushes to `main` must execute each promotion check in order and create each eligible artifact.

### P2-1: The promotion wait can miss an older open run

Status: fixed in `8179c98`.

Open at: `4779565a5e318e6f89c31fff2fd807f28cc81e3b`.

File: `.github/workflows/night-promote.yml:58-60`.

Trigger: 51 or more earlier promotion runs exist. The first 50 runs are complete, but an older run remains open.

Expected: each push waits for every earlier promotion run to end before it reads the facts (D-1202).

Actual: at `4779565`, the query requested one page of 50 runs and could omit the older open run. Commit `8179c98` now reads every page for each open status and sorts unique run ids.

Consequence: at the reviewed round, this run could check and publish its promotion before an earlier push finished. The correction restores the ordered wait.

Evidence: the script requests `per_page=50` without pagination. GitHub documents a 50-item page here and a maximum of 100 per page in its [workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs). `NightWorkflowTests.EachPushKeepsItsPromotionRunInTheOrderOfThePushes` does not cover runs beyond the first page.

Correction: `8179c98` reads all pages per status. Commit `132942b` also queries statuses in lifecycle order, so a run that advances between queries appears in a later query.

Regression check: `NightWorkflowTests.EachPushKeepsItsPromotionRunInTheOrderOfThePushes` asserts pagination and lifecycle order. It passes at `132942b`.
