## Findings

### P1-1: Enemy records omit the required body size and map consistency check

Status: fixed in `ef02f4a`.

File: `TheThingBelow.Core/Battles/EnemyRecord.cs:23-32,75-122`, `TheThingBelow.Core/Content/ContentSet.cs:209-233`.

Trigger: Load a supported content set whose map patrol names an enemy record but declares a different `size` from the enemy definition.

Expected: The enemy record declares the body size, and content loading rejects a map whose size disagrees with that record (D-754, D-206, D-209, D-236, T-2).

Actual at `fd97eb2`: `EnemyRecord` stored only id, stats, and ability ids. `Patrol` parsed and stored the map `Size`, but `ContentSet.Load` performed no map-to-enemy size comparison. The mismatched content loaded without an error.

Consequence: The same enemy can have different body dimensions in the battle record and map record. Map blocking and body-fit validation can then use a size that does not match the enemy definition.

Correction: `ef02f4a` adds the size field and validates each patrol against the largest enemy record of its group, including waiting enemies, as selected by D-788. The error names the map, patrol, group, enemy, and both sizes.

Regression check: `EnemyRecordTests.AMapWhoseSizeDiffersFromTheRecordFailsTheContentSet` changes the brute record to `boss` and proves that the fixture map fails with the map, patrol, group, enemy, and both sizes. The test failed at `fd97eb2` and passes at `ef02f4a`. `AWaitingEnemyCountsForTheSizeOfTheGroup` covers the adjacent waiting-enemy boundary.
