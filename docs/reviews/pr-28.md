## Findings

### P2-1: Rule entry ids are not checked against their file kind

Status: open.

File: `TheThingBelow.Core/Content/ContentSet.cs:130-143`.

Trigger: A rule file under `content/rules/fixtures/` contains an entry id with another kind, such as `enemy.cave_rat`.

Expected: The id kind agrees with the file that holds the entry. D-646 also names a test for this rule, and OQ-63 says PR-5 writes that test.

Actual: `AddRuleFile` parses the id, checks only whether the full id repeats, and adds it to the set. A disposable checkout with `fixture.lamp` changed to `enemy.cave_rat` passed `content-hash --write` and wrote a new hash.

Consequence: A malformed id can enter the content set under the wrong kind. Readers cannot rely on the kind portion of a permanent id to match the record that owns it (D-166, D-646).

Correction: Check the parsed id kind against the kind owned by the rule file before adding the entry. Add a regression test that gives a fixture file an id of another kind and checks that the error names the file and id.

Regression check: The new mismatch test must fail on `55eb083`. Run the test suite with `make verify`.
