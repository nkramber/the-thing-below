## Findings

### P2-1: Rule entry ids are not checked against their file kind

Status: fixed in `2b1f7f8a8c0601193eec0b4852ce5959a4c85593`.

File: `TheThingBelow.Core/Content/ContentSet.cs:130-143`.

Trigger: A rule file under `content/rules/fixtures/` contains an entry id with another kind, such as `enemy.cave_rat`.

Expected: The id kind agrees with the file that holds the entry. D-646 also names a test for this rule, and OQ-63 says PR-5 writes that test.

Actual at `55eb083`: `AddRuleFile` parsed the id, checked only whether the full id repeated, and added it to the set. A disposable checkout with `fixture.lamp` changed to `enemy.cave_rat` passed `content-hash --write` and wrote a new hash.

Consequence: A malformed id can enter the content set under the wrong kind. Readers cannot rely on the kind portion of a permanent id to match the record that owns it (D-166, D-646).

Correction: `RuleFixture.IdKind` defines the entry kind, and `ContentReader.ReadContentId(kind)` checks each fixture id against it. The error names the file, field, id, both kinds, and D-646. The `label` field remains kind-free because string ids can use `label` or `ui` (G-7).

Regression check: `ContentReaderTests.AnEntryIdOfAnotherKindFails` covers `enemy`, `item`, and `label`. The response records all three assertions failing on old head `55eb083` because no exception was thrown. `ContentReaderTests.AStringIdTakesAKindOfItsOwn` covers the adjacent valid label case, and `CheckoutContentTests.EveryRuleEntryOfTheCheckoutCarriesTheKindOfItsRecord` checks the repository content.
