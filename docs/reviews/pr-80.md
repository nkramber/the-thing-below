## Findings

### P2-1: Concurrent file growth bypasses the read cap

Status: fixed in `8175992a7500caf8002f09cee9a44a6e16b3c7c9`.

Open at: `29615cb0a1a4bf2786083e213ef55d69f1456a36`.

File: `TheThingBelow.Storage/FileText.cs:33-39`.

Trigger: another process grows or replaces a file after `FileInfo.Length` returns and before `File.ReadAllBytes` opens it. This trigger passed at `29615cb`.

Expected: `FileText.Read` must read no more than `mostBytes`, as its contract states and F-129 requires.

Actual: the code checks the old file length, then `ReadAllBytes` allocates from the size at open time. Growth in this interval bypasses the cap.

Consequence: an external file change can cause an unbounded allocation and terminate the game with memory pressure.

Correction: `FileText.Read` opens one stream, and `ReadStream` counts bytes and fails at the first byte above `mostBytes`. Commit `3559ee4` also sizes the memory buffer from the stream length, clamped to the cap.

Regression check: `FileTextTests.AStreamThatGrowsPastTheCapDuringTheReadFailsAtTheCap` and `AStreamOfExactlyTheCapReads` pass at `3559ee4`. They establish the original trigger and the exact-cap boundary. The buffer capacity uses the checked length as a hint, and the counted loop remains the size limit.
