## Findings

### P2-1: Resume can revive an enemy that map memory keeps dead

Status: open.

Open at: `6a9eb1ae32fca8a41830ce88c46fba7725bacbd5`.

File: `TheThingBelow.Core/Maps/MapState.cs:232-235`.

Trigger: A save holds a dead enemy in `PlaceValues`. A later content revision adds that enemy to the current patrol list, or changes its time station so the current map now places it. The saved patrol values have no entry for that newly placed patrol.

Expected: Map memory keeps a killed enemy dead until a reopen flag turns on (D-555). Resume across content drift keeps that memory when the new map still places the enemy (D-1111).

Actual: `MapState.Resume` calls `MapPatrols.Resume` with the saved patrol values but not the `PlaceState`. `ResumeById` starts a patrol with no saved entry alive, even when `PlaceState` holds its id as dead.

Consequence: The enemy can fight again before a reopen event. If the party wins, `BattleTurns` calls `MarkDead` for an id that the memory already holds. That throws during simulation.

Correction: Reconcile resumed patrols with the memory of the map. A patrol that the memory holds as dead must stay dead when resume adds it or restores its saved value.

Regression check: Add a resume-drift test with dead memory and a newly placed patrol with no saved patrol value. Resume must keep the patrol dead. After a reopen flag and a map re-entry, it must return alive. Run `make verify`.
